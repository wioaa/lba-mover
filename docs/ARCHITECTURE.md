# 架构说明

本文回答三个问题：**东西在哪、谁负责什么、数据怎么流**。取舍理由单独写在
第 8 节，因为"为什么不用另一个方案"比"用了哪个"更容易被后来的改动破坏。

---

## 1. 分层与依赖方向

```
            ┌──────────────────────────────────────────┐
            │  ui/          PySide6 桌面端              │
            │  只依赖 contract + 少量 engine 门面        │
            └───────────────┬──────────────────────────┘
                            │ 命令（commands）/ 事件（events）
            ┌───────────────▼──────────────────────────┐
            │  contract/    纯数据：枚举 / 模型 / 端口    │
            │  零第三方依赖，引擎与 UI 的唯一共享词汇     │
            └───────────────┬──────────────────────────┘
                            │ 实现
            ┌───────────────▼──────────────────────────┐
            │  engine/      扫描 / 规划 / 调度 / 流水线   │
            └───────────────┬──────────────────────────┘
                            │ 块读写（BlockDevice 协议）
            ┌───────────────▼──────────────────────────┐
            │  devices/     内存 / 镜像文件 / Windows 原始卷│
            └───────────────┬──────────────────────────┘
                            │ 卷枚举、错误分类、提权
            ┌───────────────▼──────────────────────────┐
            │  platform/    ctypes 封装，唯一的平台相关层  │
            └──────────────────────────────────────────┘
```

依赖**只向下**。由此得到三个可验证的结论：

* `engine` 里 import 不到 `PySide6`（可以 grep 验证），所以引擎能在无 GUI 的
  CI 上跑完整流程；
* `contract` 里 import 不到 `engine`/`devices`，所以 UI 能用假引擎单测；
* 平台差异全部收敛在 `devices/win32.py` 与 `platform/`，引擎里没有
  `if sys.platform`。

## 3. 数据流转

### 3.1 扫描流（不写盘）

```
VolumePicker 选中卷
   → UpdateTarget(volume, params, strategy)
   → [engine 线程] EngineCore.set_target → EngineCore.scan
        → FileCatalog.list_files / free_extents
        → engine.frag.analyze：规范化区间 → 分桶 → 出指标
        → FragMapEvent
   → [GUI 线程] FragMap.set_report / 指标块 / 最值得整理列表
   → EngineCore.make_plan（同一命令内跑，保证预览与执行参数一致）
        → PlanEvent
```

### 3.2 执行流（写盘）

```
ControlBar「开始整理」
   → 危险确认（系统卷要求手输盘符）
   → StartJob(JobSpec)
   → [engine 线程] scan → make_plan → validate_plan
        → JobRunner.run(plan, resume)
             ├─ 已完成 op 直接跳过（计入进度）
             ├─ ThreadPoolExecutor(max_workers = 1 若 requires_serial)
             │     └─ 每个 op → ChunkPipeline.run_op
             │           生产者线程：read_blocks（带重试）
             │                    ↓ 有界队列（深度 = queue_depth）
             │           消费者线程：write_blocks + 可选回读校验 + 限速
             ├─ 每个 op 完成 → 断点原子落盘 + JSONL 流水
             └─ 每 N 个 chunk → 进度事件（节流 12.5 Hz）
   → ProgressEvent / JobDoneEvent
   → [GUI 线程] 进度卡 / 速率曲线 / 日志
```

### 3.3 线程模型

| 线程 | 数量 | 职责 |
| --- | --- | --- |
| GUI 线程 | 1 | 只画界面、只发命令；不做任何 IO |
| engine 线程 | 1 | 串行消费命令队列，跑扫描/规划/执行 |
| op 工作线程 | 1..concurrency | 每个 op 一条流水线 |
| 读线程 | 每 op 1 条 | 预取 chunk 进有界队列 |

暂停/继续/停止**不走命令队列**——它们在线程外直接作用于 `RunControl`。
否则任务跑起来后队列没人消费，暂停命令会永远排队（旧版"取消没反应"的根因）。

## 4. 核心算法

### 4.1 分块映射（`chunk.py`）

一个 op 的多个源 extent 在盘上不连续，搬到目标时**紧密拼接**：

```
目标地址 = op.dst_start + 该 op 内已累计的块数      ← 不是"源地址 + 位移"
```

写成后者是最常见的实现错误，且只有多 extent 用例会暴露。`slice_move_op`
的返回值保证 `dst_lba` 单调且无缝。

### 4.2 碎片指标（`frag.py` / `models.py`）

| 指标 | 定义 | 为什么要这个 |
| --- | --- | --- |
| `FileFrag.frag_score` | `1 - 最大段 / 总块数` | 对"大文件被切成两半"敏感，对"一堆小段里最大那段很大"不过度惩罚 |
| `FragReport.file_frag_score` | 按块数加权平均 | 避免 100 个 1KB 小文件把指标拉满 |
| `FragReport.free_frag_score` | `1 - 最大连续自由区 / 自由块数` | 「还能不能放下一个大文件」的直接指标 |
| `Bucket.frag_ratio` | 桶内 extent 数 / 桶长，按"每 4 块一个边界"为满值 | 只用于画图；标定成 1/8 会让任何桶一有 extent 就 25% 热，整条带变成均匀底色 |

只有**文件**的 extent 参与密度统计。自由区通常是一整块大 extent，让它计入
会给每个桶都 +1，热力带变成均匀底色，信息量为零。

### 4.3 规划不变量（`planner.py` / `alloc.py`）

> 任何 op 的目标区，都不得覆盖**尚未搬走**的文件的源区。

违反它的后果不是效率低，而是读到一半的源数据被自己的写入覆盖——**永久丢失**。

实现方式：

1. 维护 `blocked`（还没搬的文件占的块）。处理某个文件前先把它自己从
   `blocked` 中**按区间**挖掉（不是丢掉整段，合并后的段常横跨多个文件）；
2. 分配时 `avoid = blocked ∪ 该文件自己的全部 extent`——自己的源区也不能当
   目标，否则自我覆盖；
3. 分配成功后把它的旧 extent 释放回自由空间，后续 op 可以复用；
4. 若任一 op 的目标落在**另一个 op 的源区**上，置 `Plan.requires_serial=True`，
   调度器强制单线程执行。这是正确性要求，不是性能妥协。

`validate_plan()` 在执行前再查一遍：越界、自我覆盖、目标互相重叠、以及
"声明可并行却存在目标踩源"。有问题直接 `PlanRejected`，一块都不写。

### 4.4 流水线（`pipeline.py`）

```
生产者线程                        消费者（工作线程）
read chunk N   ──► 队列(深度 D) ──► write chunk N + 校验
read chunk N+1 ──►              ──► write chunk N+1
```

* **队列有界**：在途数据 ≤ `chunk_blocks × block_size × queue_depth`。
  无界队列会让 2TB 的卷把内存吃满——这是"假流式"最常见的形态；
* **顺序保持**：断点记录"已写前 K 块"依赖这一点；
* **取消后排空队列**：直接退出会让生产者永久阻塞在 `put()`，线程泄漏。

### 4.5 断点（`checkpoint.py`）

* 落盘用「临时文件 + `os.replace`」，掉电不会留下半截 JSON；
* 断点带 `plan_hash`，计划变了就拒绝续做——用旧断点会把「A 位置写完」
  错当成「B 位置已完成」，属于静默数据损坏；
* 损坏的断点文件改名 `.bad` 留证，不静默覆盖；
* 流水是 JSONL 追加，尾部半行跳过、不影响前面的记录。

### 4.6 重试（`retry.py`）

* 只重试 `ErrorClass.RETRYABLE` / `VERIFY_MISMATCH`；
* 未知错误码一律 `FATAL`——"多做一次写"的代价可能是数据损坏；
* 指数退避 + ±35% 抖动，避免多个 worker 同步撞击故障点；
* 有上限：无上限重试会把"任务失败"变成"任务永不结束"。

### 4.7 调度与限速（`scheduler.py`）

* 并发 = `1` 若 `plan.requires_serial`，否则 `params.concurrency`；
* 令牌桶限速，桶容量至少一次请求量（否则小桶 + 大 chunk 会永久空转——
  这条是测试抓出来的真实缺陷）；
* 每个 op 结束落断点；全部成功且无失败才清断点（`EngineCore.execute`）。

**失败容忍：两条独立的连续计数。** 熔断回答的是"还要不要继续搬别的文件"，
而错误分类回答的是"要不要重试这个文件"——这是两个问题，用同一个计数器回答
就会出事。

| 阶段 | 连续阈值 | 含义 |
| --- | --- | --- |
| 打开文件 | `MAX_CONSECUTIVE_UNOPENABLE = 200` | 单个文件现在搬不了，跳过就该继续 |
| 其它（复核布局 / 搬簇 / 读写 / 校验） | `MAX_CONSECUTIVE_FAILURES = 20` | 说明扫描结果过期或设备不可靠 |

两者互相清零：出现系统级失败就把"打不开"的连击归零，反之亦然。

这条是 2026-11-01 真机报告逼出来的。F: 卷、`relocate_tail`、整卷，1.2 秒内
完成 0 / 失败 20 后熔断，一个文件都没搬成。失败明细里 17 个是
`Steam\logs` 下的 `winerror=32`，3 个是正在被写入的文件（bt 做种的 mp4、
Audition 刚输出的 wav、Steam 的 `appinfo.vdf`）布局复核不通过。

为什么会被"一整批占用"打成熔断：规划按**物理 LCN** 排序（`_order_by_lcn`），
同一目录下同时创建的小文件在盘上紧挨着，于是在任务队列里也连在一起。Steam
只要开着，那二十个 `.txt` 就是连续命中。用同一个计数器数，等于让"关掉 Steam
就好"把真正的系统故障线索淹没；而 200 这个数只有在整卷都拿不到句柄时才会到。

### 4.8 NTFS 文件表解析（`ntfs/`）

真机扫描的唯一数据来源。链路：

```
引导扇区 → $MFT 记录 0 的 runlist → 按 runlist 顺序扫全表
        → 每条记录：fixup 还原 → 属性解析 → 无名 $DATA 的 runlist
        → FILE_NAME 的父引用上溯还原路径
        → $Bitmap 位图得出**真实**自由空间
        → 簇区间 × (簇大小/块大小) → 引擎的 Extent
```

三处最容易静默出错、写错也不报错的地方：

1. **runlist 的增量基准是「上一段 run 的起始 LCN」**，不是上一段末尾。写成末尾
   的话，第二段起整体偏移"上一段长度"个簇——读出来的是别人家的数据，而且
   结构完全合法。
2. **fixup 必须先还原**。每个扇区末尾 2 字节被替换成 USN，真实值存在记录头的
   USA 数组里。不还原只在跨扇区时出错，是最难查的一类。
3. **USN 不匹配 = 记录被撕裂**，该记录必须整条丢弃并计数，不能"尽力解析"。

跳过策略（不是能力不足，而是搬了会出事）：

| 跳过对象 | 原因 |
| --- | --- |
| 记录号 < 16 的元文件 | `$MFT`/`$LogFile`/`$Bitmap` 位置被系统写死 |
| 目录 | 没有簇数据 |
| 常驻（resident）小文件 | 数据在记录里，没有独立簇 |
| 含 `ATTRIBUTE_LIST` | runlist 分散在额外记录里，本版不解 |
| 稀疏 / 压缩 / 加密 | 逻辑簇 ≠ 物理簇，搬簇语义改变 |
| 重解析点 | 搬走后指向关系可能失效 |

### 4.9 保护层（`engine/safety.py`）

判定只有一处 `ProtectionPolicy`，但**收敛两次**：

* `screen()` —— 规划前过滤，被拦的文件根本不进计划；
* `audit_plan()` —— 执行前复核，任何漏网之鱼让整份计划被拒绝。

两道都做，因为"规划时过滤了"依赖每个调用方都记得，而调用方只会越来越多。

审计还带空间闸门：搬完必须剩 `max(5% 卷容量, min(4096 块, 卷容量/20))`。
绝对下限不能压过比例下限——小卷上"至少留 4096 块"不可能满足，一刀切会把
所有小卷判死。

### 4.10 执行器：两条落盘路径（`engine/executor.py`）

| 执行器 | 适用 | 落盘方式 |
| --- | --- | --- |
| `BlockCopyExecutor` | 内存盘 / 镜像文件 | 逐块 读→写，可回读校验 |
| `NtfsMoveExecutor` | 真机 NTFS | `FSCTL_MOVE_FILE`，文件系统自己搬簇并更新元数据 |

**真机不能用裸块拷贝**：只动数据区不改 `$MFT` 的 runlist，文件系统看到的是
"数据莫名其妙变了"，必然损坏。所以真机必须走 MOVE_FILE。

三个由此推出的设计：

1. **执行器用工厂注入**（`factory(runner) -> Executor`），因为执行器要拿
   runner 的回调与限速器，而那两样在 runner 构造完之后才存在。
2. **MOVE_FILE 要求卷不被锁定**，与"裸写必须先锁卷"正好相反。所以真机路径
   **不打开** `Win32VolumeDevice`（它在写入前强制锁卷），自己开一个不锁的卷
   句柄 + 逐个文件句柄。
3. **搬之前必须重新查一次布局**（`FSCTL_GET_RETRIEVAL_POINTERS`）并与扫描
   结果比对。扫描到执行之间文件可能被别的程序挪过；照旧计划搬会搬到错误的
   位置。比对允许"两段合并成一段"这类等价差异，但任何一段 LCN 对不上就拒绝。

op 内断点（`start_blocks`）在 NTFS 路径上**被刻意忽略**：MOVE_FILE 一次搬一段
连续簇，中途失败会留下"一部分在新位置"的混合状态，按旧断点跳块没有意义。
op 级断点（整个文件已完成）仍然有效。

## 4.11 规划器的复杂度陷阱（踩过）

规划在真实卷上曾**跑不完**（>240s 不返回，界面停在"规划中…"）。四处热点，
每一处单独看都"只是常数"，合起来是组合爆炸：

| 位置 | 原写法 | 复杂度 | 现写法 |
| --- | --- | --- | --- |
| `planner` 逐文件禁区 | 每个文件复制一份 `IntervalSet` | O(文件 × 区间) | 直接用 `blocked`，分配后再 subtract |
| `FreeSpaceMap.allocate` | 每段空闲区 `_subtract(ext, 全部 avoid)` | O(空闲段 × 区间 × 文件) | 二分定位 `overlap_range` |
| `_needs_serial` / `validate_plan` | 双重循环 | O(op²) | 源区间排序 + 二分 |
| `_consume` / `release` | 每次整表 `merge_extents` | O(op × n log n) | 有序表二分 + 局部切片 |

R: 卷（3937 文件 / 2184 op）实测：coalesce **>240s → 2.1s**，relocate_tail 17s → 2.1s。

因为改的是"写到哪里"的核心，同时加了 80 例**随机对拍**（`tests/test_alloc_property.py`）：
用逐块布尔数组的朴素实现当基准，比对 `subtract` 与连续分配/归还的结果。
第一次跑就红了——但错的是参考实现（把从未属于集合的区域也算作"剩余"）。
对拍的价值就在这里：逼你把"什么才算正确"写成可执行的定义。

## 4.12 半锁定：簇区间的共享锁（`executor.py` / `pipeline.py` / `devices/win32.py`）

**要解决的问题**：真机报告里 20 个失败有 3 个是「布局复核不通过」——扫描时
VCN 32768 映射到 LCN 50099630，执行时变成了 341245428。那三个文件当时分别
在被 qBittorrent 做种、被 Audition 写入、被 Steam 改写。**扫描与执行之间的
时间窗，是外部进程改文件的唯一机会**，半锁定就是把这段窗口关掉。

### 实现方式：`LockFileEx` 共享锁

| 候选 | 结论 |
| --- | --- |
| **`LockFileEx`（不带 `EXCLUSIVE`）** | ✅ 采用。字节范围锁，天然对齐"部分簇"；共享锁语义 = 允许多人读、不许任何人写 |
| `FSCTL_MARK_HANDLE` + `PROTECT_CLUSTERS` | ✗ 需要 `SeManageVolumePrivilege`，且是给 defrag 工具用的"建议"，不阻止写入 |
| `FSCTL_REQUEST_OPLOCK` | ✗ 机会锁会在别人访问时把我们打断，方向反了 |
| `FSCTL_LOCK_VOLUME` | ✗ 整卷独占，锁上之后连文件都打不开 |

关键决定是**不加 `LOCKFILE_EXCLUSIVE_LOCK`**：

* 独占锁会连读一起挡住 —— 用户整理磁盘时那个视频就播不了了；
* 共享锁挡住的是**想独占的访问**，而写操作必然要独占。所以"允许读、禁止写"
  这件事不需要额外的机制，共享锁本身就是它。

`LOCKFILE_FAIL_IMMEDIATELY` 不是可选优化：不加它，撞上别人已持有的锁会
**阻塞**，整个整理任务卡在一次系统调用里，连「停止」都按不动。

### 半锁定簇区间的界定规则

```
锁的字节偏移 = 该段之前所有 Extent 的长度之和 × 簇大小
锁的字节长度 = 该段 Extent 的长度 × 簇大小
```

三条必须写死的规则：

1. **按 VCN 累加，不按 LCN 排序**。`Extent` 列表是文件内顺序；若按物理位置
   排序再累加，算出来的偏移与文件内容错位，锁到的是别的数据 —— 而"锁住了"
   这个假象会让后面的布局复核也失效（复核比的是 VCN→LCN，锁错地方它照样
   通过）。`lock_ranges()` 的注释就是钉这一条。
2. **逐段锁，段与段之间的空洞不锁**。空洞里的簇属于别的文件，替它上锁既
   没必要，也可能挡住与我们无关的写入。「部分簇范围」的字面意思就是这个。
3. **长度必须大于 0**。`LockFileEx` 把长度 0 解释为"一直锁到文件末尾"，
   一次参数写错就把整个文件锁死，所以入口直接拒绝。

### 与现有流程的衔接点

```
open_file ──► [lock_range × N] ──► query(布局) ──► layout_mismatch ──► move × chunk ──► [unlock] ──► close
```

* **加锁必须在 `query` 之前**。先读布局再加锁的话，那个窗口还在，等于白锁。
* 加锁失败**不阻止搬运**：锁是"降低被改概率"的增强，不是正确性前提。布局
  复核那一步仍然会把关，扫描结果过期照样会被拦下。失败次数记在
  `NtfsMoveExecutor.lock_failures`，上层据此告诉用户"这次锁没生效"。
* 假后端没有 `lock_range` 时**静默跳过**（`getattr` 探测）：那不是锁失败，
  是这套后端根本没有锁。

### 读取侧的同一把锁

`ChunkPipeline._read_slice()`：开关打开时，每读一个 slice 之前锁住对应的
字节范围，读完立刻释放。重试时**重新加锁**，而不是沿用上一次可能已失效的锁。

读取侧的落点是 `BlockDeviceBase.lock_range()`，默认返回 `False`（内存盘没有
外部写入者，锁无处可加也没有意义）；`ImageDevice` 用 `msvcrt.get_osfhandle`
把文件描述符换成内核句柄后调用同一个 `Win32Native.lock_file_range`。

### 异常情况下的释放

三层兜底，从上到下越来越"不可控但一定生效"：

1. **正常路径**：`finally` 里 `_release_op_ranges()` 逐段 `UnlockFileEx`，
   **在 `close_file` 之前**（关句柄本身也会释放锁，但显式解锁让持有区间在
   代码里看得见，不依赖"没人提前 return 忘掉它"）。
2. **搬簇中途抛错 / 取消**：同一个 `finally` 覆盖，锁不会泄漏。
3. **进程崩溃 / 被强杀**：Windows 在句柄关闭时释放该句柄持有的全部范围锁。
   锁是**绑定在句柄上**的，这是它比"自己维护一张锁表"更可靠的地方。

解锁失败不改变这个文件的结论：句柄紧接着就关掉，关闭即释放。

## 4.13 整理强度：与模式正交的第二维度（`contract/enums.py` / `engine/planner.py`）

### 为什么拆

2.0.0H 之前，"往哪搬"和"动多少"是同一件事，都写死在 `Strategy` 里：

| 策略 | 文件集（写死在策略里） |
|---|---|
| `COALESCE` | 仅碎片文件 |
| `COMPACT` | 全部文件 |
| `RELOCATE_TAIL` | 仅碎片文件 |

于是"我想更彻底一点"没有任何入口。想动全部文件就得从「合并碎片」换成
「向卷首聚拢」——**落点方向也跟着变了**。用户只能猜，猜错就是几小时的重排。

现在分成两个维度：

* `Strategy` 回答"往哪搬、怎么搬"：落点方向与顺序；
* `Intensity` 回答"动多大一片"：**选哪些文件**。

`select_files()` 里策略只用来识别两个特例（`ANALYZE_ONLY` 不选、
`RECLAIM` 不看强度），其余模式下的筛选**完全由强度决定**。

### 五档的界定

| 档位 | 文件集 | 说明 |
|---|---|---|
| `FAST` 快速 | 碎片收益前 20%，≤500 个 | 收益 = `(段数-1) × 每段平均块数` |
| `STANDARD` 标准 | 全部碎片文件 | **与 2.0.0H 之前完全一致**，升级不改行为 |
| `DEEP` 深度 | 碎片文件 + 不足 1 MiB 的连续文件 | 小文件散着会把连续空间切成小洞，成批归位才划算 |
| `THOROUGH` 彻底 | 全部文件，无下限 | 连本来连续的也重排 |
| `EXTREME` 极端 | 仅 ≥`extreme_min_mib`（默认 256）的大文件，按体积降序 | 体积维度切最大的一批 |

三条刻意的设计：

1. **`EXTREME` 不在包含链上**。前四档是"依次放宽"，极端档是**换了个切法**：
   只按体积切，哪怕那文件本来一整个连续。它要解决的是"把占了半盘的大文件
   一次性归位，腾出大片连续区"，不是"治所有碎片"。所以它可能比标准档动得
   更少文件、搬更多字节。
2. **`FAST` 的 20% 有下限保护**：`max(1, ...)`。只有一个碎片文件时"前 20%"
   算出来是 0 个，而用户点快速是想做一点事，不是想什么都不做。
3. **`FAST` 有 500 个的绝对上限**。几十万文件的卷上纯比例会挑出几万个，
   那已经不是"快速"了。

### 排序

`EXTREME` 按体积**降序**：最大的先搬。它最难找落点，最后放会剩一块谁都塞
不进去的洞。其余档位沿用策略自己的顺序（`COMPACT` 按 LCN 升序，其它按碎片
收益降序）。

### 约束式任务不看强度

`RECLAIM` 必须搬开目标区内**全部**挡路的文件，不能因为选了"快速"就只搬
20%——那会给出"大概腾出了"的假结果，而用户是按这个数字去规划下一步的
（装虚拟机、拷大文件）。界面上此时整行档位禁用并写明原因，而不是留一个
能点但无效的控件。

### 空集要说清原因

挑不出文件时不能一律说"未发现碎片"。极端档下那句话是谎言：卷里可能有几万
个碎片文件，只是没有一个达到体积门槛。`_empty_reason()` 会报出当前最大文件
有多大、门槛是多少、下一步该调低阈值还是换档——否则用户看到"没有需要整理
的文件"会以为盘很健康，然后放弃这个功能。

### 界面的默认档随模式走

切模式时带出该模式的默认档（`DEFAULT_INTENSITY`）：

| 模式 | 默认档 | 理由 |
|---|---|---|
| 合并碎片 | 标准 | 旧语义就是碎片文件 |
| 向卷首聚拢 | **彻底** | 旧语义是**全部文件**，用标准档就成了静默缩水 |
| 搬到卷尾 | 标准 | 旧语义就是碎片文件 |
| 腾出空间 / 只分析 | — | 档位不适用，整行禁用 |

这不是绑定：带出之后用户仍可自由改档位。

### 界面上的一个坑

五个档位按钮如果按内容的 `minimumSizeHint` 排，QSS 的 padding 会把每个撑到
81px，五个加起来正好跟面板可用宽度打平（421 vs 421）——DPI 一缩放第 5 个
就被裁掉，用户看得见「彻底」却点不到「极端」，而界面上没有任何提示。
必须显式 `setMinimumSize(40, 26)` 把下限压下来。`test_ui_intensity.py`
里有一条几何断言专门盯这个：比较最后一个按钮的右边界与面板宽度，因为
"按钮存在、可点、`isVisible()` 为真"这三条它全都满足。

## 4.14 尾部压实：把卷尾数据紧贴末尾重排（`Strategy.PACK_TAIL`）

`RELOCATE_TAIL` 和它看起来像，其实是两件事：

| | `RELOCATE_TAIL` | `PACK_TAIL` |
|---|---|---|
| 选哪些文件 | 只挑碎片文件 | 范围内**全部**数据，含本来就连续的 |
| 落点 | first-fit 往尾部填空档 | 从卷尾往前**依次堆叠** |
| 结果 | 填了，但中间仍可能有洞 | 数据区连续、其前方一整块连续空闲 |

### 算法：一条从尾向前的游标

```
cursor = 卷尾（减去保留区）
按文件「末尾 LCN」降序排列，依次处理：
    若文件是单段且末尾正好等于 cursor  →  它已在位，cursor 前移到它的起点
    否则先试 [cursor - n, cursor)       →  紧贴（压实质量最好）
    紧贴放不下（2.0.0K 起）             →  在已压实区之前找最靠后的连续空闲
    连这段也找不到                      →  当作已就位，cursor 退到它起点
```

按 `末尾 LCN` 降序是关键：最靠尾的先搬，它一搬走，腾出的空间正好给下一个。
反过来先搬靠前的，会把还没读的源数据压掉。

### 「紧贴放不下就跳过」为什么必须改掉

旧实现只认「紧贴 cursor」这一种落点。大文件需要一段 `n` 块的**连续**空闲，
而紧贴 cursor 的那一段通常还被尚未搬走的数据占着（按顺序还没轮到它），
于是大文件一个都搬不动 —— 表现出来就是**「压实只对小文件起效」**。

2.0.0K 改成两级：先试紧贴，不行就用 `FreeSpaceMap.allocate(..., from_tail=True,
max_end=cursor)` 在已压实区之前取最靠后的一段连续空闲。安全性与 `covers`
完全等价 —— 两者都只从自由表里取，而未搬走文件的块根本不在自由表里。
代价是压实区内部会留下空隙，这个量会算进 `notes` 并如实报出。

落点在前面时**游标不前移**：把 cursor 拉过去会让中间所有数据失去「往尾部聚」
的约束，压实就退化成乱搬。那块空隙留给后面更小的文件去填（它们优先紧贴）。

### 强度在压实下的语义（与其它模式不同）

其它模式里强度回答「挑多少文件才有收益」，压实回答「为了完整性愿意付多少
搬运量」：

| 档位 | 压实下的含义 |
|---|---|
| 快速 | 只搬多段文件 —— 只有它们在自身地址空间里留洞 |
| 标准 | 范围内全部数据，贴不紧时改放前面最近的空位 |
| 深度 | 同「标准」：压实不区分文件大小，多搬大文件只会更慢 |
| 彻底 | 全部数据，**且必须紧贴** —— 放不进去的文件就不动，不留空隙 |
| 极端 | 只搬 ≥「大文件下限」的文件 |

「深度 = 标准」是刻意的：编一个假的差异不如在说明行里写清楚。旧版把整行
强度禁用（理由是「压实要看全部数据」），结果用户唯一能调的只剩范围 ——
而真正需要调的「要不要动大文件」没有入口。

### 两个必须守住的性质

**① 每个 op 的目标区在规划时就必须是空的。** 逐个用
`FreeSpaceMap.covers()` 检查（O(log n)，不能用 `is_free` —— 后者每次重建
`IntervalSet`，在"每个文件查一次"的循环里退化成 O(文件数 × 段数)）。

**② 目标区可以踩别的 op 的源区，但必须串行。** 压实的本质就是"后者搬进前者
腾出的位置"，所以 `requires_serial=True` 是**常态**而不是异常。测试里用
"按 op 顺序模拟执行"来验证：每一步写之前，目标区必须不在已占用集合里。

### 压不动的要说出来

真的连 `n` 块连续空闲都找不到时，这些文件留在原地，**会在压实数据区里留下
洞** —— 必须具名报出（`notes` 里写"N 个文件既找不到紧贴位置、也没有足够大的
连续空闲（例如 xxx）"）。否则用户看到"压实完成"却发现中间还有洞，是最难
解释的那种结果。

## 4.15 缓存搬运：两套**独立**的中转引擎

`ExecMode` 有三个值，对应三套**互不共享执行代码**的实现：

| 模式 | 中转介质 | 引擎文件 |
|---|---|---|
| `NATIVE` | 无（盘内搬簇 / 逐块直写） | `executor.py` |
| `CACHED` | 磁盘工作目录里的临时文件 | `cache_engine.py`（4.15.1） |
| `MEMCACHED` | 预分配的内存块池 | `memcache_engine.py`（4.15.2） |

不共享代码的理由是失败方式不同：`NATIVE` 错在系统调用（文件被占用、布局变了、
权限不足），`CACHED` 错在文件 IO 与容量（缓存盘满、路径不可写），`MEMCACHED`
错在内存分配（块池用完、MemoryError）。混在一个类里，任何一次调试都要同时
理解三条路径的语义。调度器只认 `run_op` / `prepare` / `close` 三样。

### 4.15.1 跨盘缓存（`engine/cache_engine.py`）

### 为什么不共享代码

`NtfsMoveExecutor` 错在系统调用（文件被占用、布局变了、权限不足），
`CachedCopyExecutor` 错在文件 IO 与容量（缓存盘满、路径不可写）。混在一个类里，
任何一次调试都要同时理解两条路径的语义。所以两者**接口相同、实现独立**，
调度器只认 `run_op`。

### 它做什么

```
读源盘 → 顺序写缓存文件 → 顺序读缓存文件 → 写目标盘
```

缓存文件一个 op 一个，按 VCN 顺序**追加**写，所以缓存盘那一侧是 100% 顺序的。
这是这个引擎唯一的性能卖点：缓存目录可以指定到另一块盘（顺序性能更好的那块）。

### 它不能做什么（硬边界）

**不能作用于已挂载的 NTFS 卷。** 裸写绕过文件系统，会覆盖 `$MFT` 指着的簇区，
文件系统当场损坏，而且损坏是"看起来成功了"的那种：数据写进去了，元数据没跟。

`EngineCore._check_exec_mode()` 在执行前拦这一条。闸门放在运行时而不是构造期，
因为 `JobParams` 在界面上随时可改，而卷是运行时才知道的。

### 顺序性指标必须分盘记

`IoStats` 把**源盘读 / 缓存盘写 / 缓存盘读 / 目标盘写**分开统计，各自算顺序率。
混成一个"顺序率"会掩盖真正的瓶颈：缓存盘的写永远满序（追加），真正会跳的是
目标盘（受文件实际布局限制）。

单段文件第一次 IO 不算"跳读" —— 没有"上一段"可比。把它算成非顺序，单段文件
会永远显示 87.5%，读数的人会以为还有优化空间。

### 缓存文件大小与预分配

写入前 `truncate` 到最终大小：让文件系统一次性预留空间，避免写入过程中反复
扩展把缓存文件切碎 —— 一碎，顺序性就没了，这个引擎也就没有意义了。

缓存文件用完即删。每个 op 一个 GB 级文件，不删就是磁盘炸弹。取消/异常路径由
`finally` 兜住。

---

### 4.15.2 内存缓存（`engine/memcache_engine.py`）

### 它解决什么

`CACHED` 把数据落到**文件**上，代价是多走两趟盘（写缓存 + 读缓存）。内存缓存
把中间那一段放进内存，于是缓存侧没有 IO。它真正的收益不是"更快"，而是：

* **多个碎读攒成一次大写**。源文件碎成 8 段 × 128 KiB、目标是一段连续的
  1 MiB 时，流式搬运要写 8 次，块池只写 1 次；
* **内存占用确定**：块池在 `prepare` 一次分配完，运行期不再增长。

### 块池的几何：两个旋钮，含义不同

| 参数 | 含义 |
|---|---|
| `mem_cache_blocks`（1..4096） | 块数。同时是**内存上限**与**读写错位深度** |
| `mem_cache_block_kib`（16..65536） | 单块大小。决定"一次能凑多长" |
| 总量上限 | 8 GiB。超了在 `JobParams` 构造期就报错 |

合成一个"总大小"旋钮就调不动这个取舍了：块大 → 目标盘小写少但延迟高；
块多 → 能提前读但内存线性涨。界面上两个数字分开摆，且内存上界把块池
**单独列出来加总**（`JobParams.total_memory_budget_bytes`），不混进流水线缓冲。

### 块满时的替换策略：先进先出

块池里每一块都是"写入一次、回写一次"，**没有重复访问**。LRU / LFU 要预测
"哪块还会被用到"，而这里每块只用一次，所以那些策略毫无意义。FIFO 是唯一
自洽的选择：最早填满的块最早回写（`_acquire_slot` → `_flush_oldest`）。

所以它其实不是"缓存"，而是一个**写回缓冲池**；名字沿用 `memcache` 只是让
"缓存搬运"这个用户概念保持一致。

### 相邻脏块合并回写

回写时若下一块的目标地址正好接在上一块末尾，就合并成一次 `write_blocks`，
上限 `coalesce_limit_bytes`（默认 4 MiB）。合并要多一次内存拷贝，所以必须有
上限 —— 否则 32 MiB 的池每次回写都要再复制 32 MiB。

**不允许跨非连续地址合并**：那会一次写跨过别人的数据。

### 断点：只统计真正写下去的块

`run_op` 返回的 `blocks_done` 必须等于"已经落到目标上的块数"。写成"读进来
多少块"就会多算 —— 而断点按这个数续做，多算一块意味着那一块永远没人写，
数据静默缺失。所以计数器只在 `_flush_oldest` 里累加。

取消时把已读进池的脏块**照样写出去**：它们的目标地址在规划时验证过是空的，
写下去只会让续做少做一点，不会写坏任何东西；丢掉反而会让计数与磁盘不一致。

### 同一个硬边界

和 `CACHED` 一样**不能作用于已挂载的 NTFS 卷**：中转介质是内存不代表写入
目标的方式变了 —— 它仍然是裸写块设备。`_check_exec_mode` 一并拦。

`uses_cluster_mover()` 也必须在缓存模式下返回 `False`：MOVE_FILE 路径刻意
不打开裸设备，而缓存引擎需要 `runner.src`；不返回 False 就是 `NoneType.read`。

## 4.16 目标区预占：占位文件（`engine/preoccupy.py`）

### 它防的与防不住的

规划时目标区是空闲的，执行时可能被别的程序写进去 —— 那一刻
`FSCTL_MOVE_FILE` 会因为目标非空而失败。

但它**只防执行那一瞬间**：占位是在"计划已定、还没开搬"的窗口里建立的，
规划阶段的抢占管不了。真机报告里那 3 个"布局复核不通过"也不是这类问题
（那是**源文件**被改，由半锁定覆盖）。

### 为什么按 op 建占位

`FSCTL_MOVE_FILE` 要求目标区完全空闲。如果用一个占位文件覆盖整个计划的
目标区，执行第一个 op 之前就得释放它 —— 释放一次就是全部放开，后面的 op
又裸露了。按 op 建，"释放这一段"和"紧接着搬进这一段"之间只隔一次 `open_file`。

### 占位文件怎么来

`SetEndOfFile` 扩到目标大小 + `SetFileValidData` 分配簇。后者是**不清零**的
分配 —— 写零要几 GiB 额外写入，比整理本身还慢。代价是文件内容为未初始化数据，
所以用隐藏属性创建、用完立刻删除。

`SetFileValidData` 需要 `SeManageVolumePrivilege`。拿不到就报错而**不降级写零**：
降级之后它比不预占还慢，那就该老老实实说"这个功能没生效"。

### 失败要降级，不要变成硬前置

占不住时搬运**照常进行**（布局复核与执行前审计才是把关的），只在日志里说明并
记 `lock_failures`。把它变成硬前置，会让这个功能在权限不足的机器上直接把整理
功能废掉。

### 未验证的部分

真机路径需要管理员权限与一块可写的 NTFS 卷，本机不具备。所以：
- 调度逻辑（占哪些区间、何时释放、失败怎么回滚）有完整的假后端测试；
- Win32 两个原语（`create_placeholder` / `delete_file`）只保证 argtypes 正确
  （**64 位长度必须显式声明**，否则会被截断成 32 位，`SetEndOfFile` 依然成功返回，
  占位文件只有一半大小而看起来一切正常）；
- 真机首次启用前，应先拿镜像/备份盘演练。

## 4.17 配置持久化：让"上次怎么设的"活到下次启动（`settings.py`）

### 为什么不用 QSettings

QSettings 在 Windows 上写注册表：用户看不到、拷不走、卸载残留，出问题时既不能
"把配置文件发给我看看"，也不能"手动改一行试试"。而参数里有一半是**危险参数**
（搬运方式、强度、半锁定），放在不可见、不可导出、不可 diff 的地方不合适。
所以用一份 JSON：人可读、可备份、可贴进 issue。

### 存哪

| 平台 | 路径 |
|---|---|
| Windows | `%APPDATA%\LBAMover\settings.json` |
| macOS / Linux | `$XDG_CONFIG_HOME/lbamover/settings.json` |
| 任意（设了环境变量） | `$LBAMOVER_CONFIG` 的完整文件路径 |

`LBAMOVER_CONFIG` 给便携版和测试用：便携版指到 exe 同级目录，配置跟盘走；
测试指到临时目录，绝不碰真实用户配置。

**不写仓库里的 `.lbamover/`**：那里放断点与流水，属于"运行输出"。混在一起会让
`git clean` 顺手清掉设置。

### 什么时候写

1. **改动后 800ms 防抖**（`SAVE_DEBOUNCE_MS`）：拖一次滑块会连发十几个
   `valueChanged`，每次都落盘既慢又无意义；800ms 足够短，强杀也只丢最后一次改动。
2. **关窗时强制落盘**，且排在 `service.stop()` **之前** —— 后者最长等 5 秒，
   而"这次的设置"是关窗后唯一还需要活下来的东西。
3. **不做"只在退出时写"**：那样崩一次就回到默认值，而这正是要修的问题。

写盘一律**原子替换**（同目录临时文件 + `os.replace` + `fsync`）：直接覆写时
断电会得到半截 JSON，下次启动只能当损坏处理，等于设置全丢。

### 坏了怎么办

配置是**便利功能**，任何异常都不能挡住主流程：

| 情况 | 处理 |
|---|---|
| 文件不存在 | 全默认，`missing=True`，日志说一句"首次启动" |
| JSON 语法错 | 备份成 `settings.json.broken-<时间戳>`，按默认启动（**不静默删除**：删掉就再也查不出为什么设置没生效） |
| 单个字段非法 | 只丢这一个，其余照常恢复，日志点名是哪个 |
| 目录不可写 / 磁盘满 | 记一条警告，界面照用；下次改配置再试 |

逐字段恢复（`_params_from`）而不是一句 `JobParams.from_dict`：后者任何一个字段
越界都会让**整份**参数回默认，用户改过的十几个选项一起消失，日志里只有一句
"参数非法"。

`exec_mode` 要**最后**应用：`JobParams` 有一条跨字段校验（`exec_mode=CACHED`
要求 `cache_dir` 非空）。先设 exec_mode 那一步会被判非法丢掉，用户看到的就是
"选了跨盘缓存，重开变成盘内搬运"。

## 4.18 规划阶段可中断（`engine/control.py` / `planner.py` / `safety.py`）

### 缺陷原样（2.0.0I 及之前）

真实卷上点「扫描 / 预演」之后，规划要跑几十秒；这段时间里：

* 「停止」按钮是**禁用的** —— `ControlBar.sync_state` 只认 `RUNNING` / `PAUSED`；
* 就算绕过界面把 `CancelJob` 塞进去，规划循环里也**一次取消检查都没有**。

用户看到的是"按钮灰着，点了没反应，只能等"。这不只是 UI 问题，是两个独立的
缺口同时存在。

### 两处一起改，缺一不可

1. **入口**：`ControlBar` 在 `SCANNING` / `PLANNING` 也启用「停止」，停止中显示
   「停止中…」并禁用（已经登记过了，再点没有意义）。
2. **出口**：规划、策略筛选（`ProtectionPolicy.screen`）、回收区审计三处长循环
   内部按 `CANCEL_CHECK_EVERY = 256` 的节奏查取消标志，查到就抛
   `PlanningCancelled`。

只改一处都是假修：只开按钮 → 按了仍然没反应；只改循环 → 按钮还是灰的。

### 状态机

`SCANNING` / `PLANNING` 增加一条到 `STOPPING` 的合法迁移。停止后由循环自己
收尾成 `CANCELLED`，**不能**落进 `EngineService._loop` 的 `"命令失败 → IDLE"`
分支 —— 那会把用户刚按下的停止显示成"什么都没发生，界面又回到可以开始的样子"。

`make_plan` 捕获 `PlanningCancelled` 后：记一条日志、置 `CANCELLED`、**不发
`PlanEvent`**、`self.plan` 保持 `None`。留下半份预演比什么都不显示更糟。

### 取消标志是一次性的

`make_plan` 在非 `STOPPING` 状态下换一块新的 `RunControl`。不这么做的话，
"停过一次 → 改强度想重新预演 → 立刻又被取消"，看起来像卡死。判定依据是
`STOPPING`：它是"有人正在等这次停止生效"的唯一状态，此时保留标志才能让
排队中的规划立刻退出。

## 5. 内存模型
内存上界只由参数决定，与卷大小无关：

```
buffer_budget = chunk_blocks × block_size × queue_depth × concurrency
```

`JobParams.buffer_budget_bytes` 就是这个乘积，UI 的参数面板实时显示它。
默认值（256 × 4KiB × 4 × 2）= 8 MiB。

分桶可视化也不构造 per-block 数组：1TB / 4KiB 有 2.6 亿块，任何
"每块一个元素"的实现都会直接 OOM。`bucketize` 一次遍历把 extent 摊到桶里。

## 6. 与 UI 的接口

### 6.1 命令（UI → 引擎，9 条）

| 命令 | 语义 |
| --- | --- |
| `UpdateTarget` | 换目标卷，可选「扫描 + 规划」预演（带 `file_ids` 时只预演这些文件） |
| `Replan` | **不重扫**，用现有报告按新范围/策略重算一次预演 |
| `StartJob` | 开始整理（带 `JobSpec` 时重新扫描并规划） |
| `PauseJob` / `ResumeJob` / `CancelJob` | 直通 `RunControl`，不进队列 |
| `SetParams` | 热更新：限速、回读校验 |
| `Shutdown` | 引擎线程退出 |

`Replan` 的存在是有原因的：用户勾完文件要立刻看到"这批会搬多少块"，而重新
扫描在百万文件的卷上要几分钟。**扫描结果与整理范围是两件事** —— 前者没变，
后者变了，就不该重扫。

### 6.2 整理范围：整卷 / 手动选文件

引擎侧的语义只有一条：`file_ids` 为**空元组 = 整卷**，非空 = 只动这些文件。
这条语义有个尖锐的后果 —— **空选择会被当成整卷**。所以：

* UI 在手动模式下没有选择时**锁住「开始整理」**，并且扫描后不预演
  （否则预览出来的"要搬 6.5 GiB"和用户只想动几个文件的意图对不上）；
* `select_files` 对"指定了但找不到"的文件分两种处理：全找不到 → 计划不可行
  并说明原因；部分找不到 → 照做，但把跳过的数量写进 `plan.notes`；
* 保护层照旧两处收敛（`screen` + `audit_plan`），**手动选择不能绕过任何一条**。

选择器的两条实现约束（都是"选错文件"级别的）：

1. **身份是 `file_id`，不是行号**。行号随筛选/排序变化，用行号当身份会出现
   "勾了 A、引擎动了 B"；模型里存的是 id 集合，`QTableView` 只负责显示。
2. **`file_id` 必须跨扫描稳定**。未提权路径曾经用遍历序号（`walk-12`），
   而 `StartJob` 会重新扫描一次 —— 序号一变，用户选的 12 个文件就指向了别的
   文件，断点续做也会被判成"计划已变化"。现在取路径（MFT 路径取记录号）。

### 6.3 扫描进度

扫描**没有总量**可算（要遍历完才知道有多少文件），所以不编百分比：

* `Progress.scanned_items` 是"已看条目数"，UI 在 `SCANNING` 状态下把进度条切成
  不确定模式（`setRange(0,0)`），数字位显示条目数，下方显示当前路径；
* 事件按 **0.2s** 节流（进度条要"在动"），日志按 **5s** 节流（日志要能翻）；
* 阶段之间（记录解析 → 组装路径）计数带基数，保证 N 只增不减 ——
  否则数字会从 46000 跳回 1000，看起来像任务重启了。

### 6.4 可用空间整理（`Strategy.RECLAIM`）

前面几个策略都是**优化式**的："尽量把碎片整理得好一点"。这一档是**约束式**的：

> 这 N 块必须是连续空闲，位置在卷首或卷尾。做不到就直说，不要给我一个"大概齐"。

它解决的是另一类需求：装虚拟机、拷镜像、给备份留一段连续空间。用户拿这个
结果去放一个 200 GiB 的文件，所以"差不多空了"等于没做。

**参数**（`JobParams`）：

| 参数 | 含义 |
| --- | --- |
| `reclaim_blocks` | 要腾出的连续空闲块数。**0 表示没设置**，直接判不可行，绝不猜一个默认值 |
| `reclaim_at` | `FreeSpaceSide.HEAD` / `.TAIL`，界面上是"卷首 / 卷尾" |
| `reclaim_avoid_protected` | 目标区撞上搬不动的占用时是否让开（默认开，理由见下） |

界面里按 GiB 输入，只在边界处换算成块一次；引擎里没有第二套单位。

**算法四步**（`planner._build_reclaim_plan`）：

1. **定目标区。** 把"搬不动的占用"（`FragReport.protected_extents`，由保护层
   筛选时留下一份）当成禁区，列出它之间的空隙，从卷首/卷尾那一侧找第一段
   够大的。
2. **收集挡路的文件。** 与目标区有任何重叠的文件**全部**要搬走 —— 不挑碎片度，
   也不看用户勾了什么。这一点和手动范围天然冲突，所以计划里会写明"忽略手动勾选"。
3. **在目标区外分配落点。** 按方向堆到另一头（腾卷首就往高位堆，反之亦然），
   并且用 `min_start` / `max_end` 把目标区彻底排除在落点之外。
4. **自检。** `_audit_reclaim` 再验一遍"没有任何落点回到目标区"；执行前的
   `audit_plan` 再验一遍"挡路文件都在 op 里、目标区没有受保护占用"。

**为什么允许让开受保护区。** NTFS 把 `$MFT` / `$LogFile` 钉死在低地址，
`pagefile.sys` 也常在固定位置。如果坚持"必须正好从第 0 块开始"，卷首模式在
真实卷上**永远失败** —— 一个只会报错的功能等于没有。所以默认整体让开，并把
"实际落在哪、为什么没贴边"写进 `plan.notes` 与 `Plan.reclaim_extent`。
想要严格语义的调用方把 `reclaim_avoid_protected=False` 打开即可。

**三条不能松的口子**：

* 落点写回目标区 = 搬了一整天、空间没到手；
* 有一个挡路文件搬不出去 = 目标区不可能全空，整单判不可行（不给"搬了一半"的计划）；
* 目标区外的空闲不够安置被搬出的文件 = 直接报差额，不硬做。

### 6.5 失败诊断：让用户能把问题说清楚

出问题时用户手里只有这个界面。旧版日志写一行 `op12 失败：R:.pst — 拒绝访问`，
用户转述时只能说"它报错了"——对方得先追问五轮才能开始排查。

现在一条失败带这些字段（`contract.models.FailureDetail`）：

| 字段 | 作用 |
| --- | --- |
| `stage` | 卡在哪一步：打开文件 / 复核布局 / 搬簇 / 读取数据 / 写入数据 / 回读校验 |
| `reason` | 人类可读的一句话 |
| `error_type` | 异常类名，能在代码里搜到抛出点 |
| `error_class` | 可重试 / 不可重试 / 校验不一致 —— 直接回答"还要不要再点一次" |
| `winerror` | Windows 错误码，`diagnostics.WINERROR_HINTS` 把它翻译成动作 |

阶段由执行器与流水线各自填（`OpResult.stage`）：真机路径在 `open_file` /
`layout_mismatch` / `move` 三处，块拷贝路径在读端与写端。少了它，日志只能说
"这个文件失败了"，而"打开失败"和"搬簇失败"的处置完全不同。

界面上日志面板右上角有**「复制诊断」**，产出 `diagnostics.build_report()` 的
一段纯文本：版本、系统、是否管理员、目标卷、策略与参数、结果统计、失败明细
（含阶段/错误码/建议）、最近 40 行日志。设计目标是"点一下、粘出去"就能开始排查。

**结局三档。** `DONE` / `PARTIAL` / `FAILED` 分别对应"全成功"、"有成功有失败"、
"一个都没成功"。合并成两档是 2.0.0E 修掉的真实问题：19 个成功 1 个失败会显示
「已完成」并配绿色，用户扫一眼就走了，而没搬走的文件还躺在碎片里。

### 6.6 事件（引擎 → UI，6 类）

`StateEvent` / `ProgressEvent` / `LogEvent` / `FragMapEvent` / `PlanEvent` /
`JobDoneEvent`。全部不可变快照，由 `ui/bridge.py` 翻译成 Qt 信号。

`EngineBridge` 是**唯一** import `QObject` 的地方（引擎侧完全不知道 Qt 存在）。

| **未提权扫描（目录遍历 + 逐文件簇映射）** | ✅ 已实现 | 不需要任何权限。真实 C: 卷 126.7 万条目 → 88.2 万文件，8 路并发后由 246s 降到约 150s（瓶颈见 7.1）。**只能预览**：拿不到 `$Bitmap`，也看不到打不开的文件 |
| `FSCTL_GET_RETRIEVAL_POINTERS` | ✅ 已实现 | METHOD_NEITHER + 按线程复用的页对齐缓冲；缓冲不足会**识别出截断并扩容**，不会把半张 runlist 当真 |
| `FSCTL_MOVE_FILE` 簇级搬迁 | ✅ 已实现 | 文件系统自己搬簇并更新元数据；**未在真实卷上验证过** |
| 原始卷块读 | ✅ 已实现 | `\\.\X:` + 页对齐缓冲 + 短读补齐 |
| 原始卷块写 | ⚠ 有条件 | 必须先 `FSCTL_LOCK_VOLUME`；对**已挂载**卷裸写必然破坏文件系统，默认拒绝 |
| exFAT / FAT32 | ⚠ 只读预览 | 没有 `$MFT`，走目录遍历出分布；不支持执行 |
| 卷镜像验收 | ✅ 可用 | `lbamover ntfs --image dump.img` |

**两条扫描路径的选择**（`engine/catalog.open_ntfs_catalog`）：

```
NTFS 且能打开 \\.\X:  →  MFT 解析（秒级，$Bitmap 给权威自由空间，restricted=False）
否则（未提权 / exFAT）→  目录遍历（分钟级，补集推自由空间，restricted=True → 只许预览）
```

这条分支的存在是产品性的：扫描是用户点下的第一颗按钮，未提权就直接报错
等于"这软件不能用在真盘上"。回落给出的仍是**真实数据**（文件→簇区间来自
文件系统本身，不是估算），只是缺了 `$Bitmap` 与打不开的文件——实测 C: 卷
这部分少算约 72 GiB（pagefile / WinSxS 内受限文件 / `$MFT` 自身），因此
受限报告**一律禁止执行**（`EngineCore.execute` 直接 `PlanRejected`，
界面同时锁住"开始整理"）。

**为什么强调"未在真实卷验证"**：解析器的每条规则都能在合成镜像上被验证，
但真实卷有大量合成镜像覆盖不到的情况——`ATTRIBUTE_LIST` 分散记录、4K 扇区、
压缩文件、`$Extend` 下的元文件、损坏记录。这些在代码里都做了跳过处理，
但"跳过"是否覆盖全，只有真盘能给出答案。上真机前请先解析一份镜像。
（这一条已经被真实卷验证过一次并抓到了问题：事务日志文件给出的 run 会首尾
重叠，`FileFrag` 直接抛错会把整卷扫描带崩——现在两边都做了归一化与单文件隔离。）

**为什么不做静默降级**：拿不到文件表时返回空报告，界面上会显示"0 个碎片
文件，卷很健康"——而事实是根本没看过。这类假象比报错危险得多。

`devices/win32.capabilities()` 会把探测结果如实上报到界面顶部的徽标，
用户能直接看到"为什么点了没反应"。

### 7.1 扫描速度：时间花在哪，能压到什么程度
扫描分四个阶段，各阶段的可压缩性完全不同。下面的数字是实测（75 GiB 数据卷
R: + 952 GiB 系统卷 C:），不是估算：

| 阶段 | 旧耗时 | 现在 | 手段 |
| --- | --- | --- | --- |
| 读 $MFT + 解析记录 | 1.46s（R:，4.6 万条） | **0.38s** | 已删除记录槽只取头部；只解析 5 种真正影响决策的属性；属性头一次 `unpack` 取全 |
| $Bitmap → 自由区间 | 2.98s（R:，1966 万簇） | **0.006s** | 按字节状态跳跃（`translate` + `find`），只处理段边界；1 TiB 卷约 0.07s |
| 目录遍历（未提权） | 0.64s（C:） | 不变 | `os.scandir` + `entry.stat()` 走目录项缓存 |
| 逐文件簇映射查询（未提权） | 206s（C:，88.2 万文件） | **约 150s** | 8 路线程并发 + 每线程复用缓冲 |

关于最后一行要说实话 —— **加速比只有 1.6~1.8 倍，这不是线程池开得不够**：
同一卷上这些调用最终都在 NTFS 的目录/记录锁上排队。用**多进程**做同样的事
实测也只有 1.3~1.6 倍，说明瓶颈在内核侧，不在 GIL。再加线程只是互相抢锁。

真正的量级差异来自换路径，不是调参数：

```
提权（管理员）  → 读一次 $MFT             88.2 万文件  ≈ 20s 量级（占用主要是 $MFT 顺序读）
未提权          → 每文件两次系统调用      88.2 万文件  ≈ 150s 且更不准（受限）
```

所以界面上"权限徽标"不是提示，而是**性能开关**：点它提权重启后，大卷的扫描
从分钟级掉到十秒级，同时拿到 `$Bitmap` 的权威自由空间、允许执行。

两条不能为了速度让步的红线：

* 位图比卷短、读不全时，缺失部分按**已用**处理 —— 少报自由空间顶多整理不动，
  多报自由空间会让规划器覆盖别人的文件。
* `FSCTL_GET_RETRIEVAL_POINTERS` 缓冲不足时驱动**不报错**，只回填一部分。
  必须按"`16 + 段数 × 16 > 实际字节数`"判定截断并扩容，否则碎文件的
  后半段会被当成空闲。

## 8. 取舍记录

| 决定 | 备选 | 为什么这么选 |
| --- | --- | --- |
| 自己解析 $MFT，不引第三方库 | 用 `mft` / `analyzeMFT` | 依赖一个不维护的库解析“会写错就毁盘”的数据，风险不对等；自己写还能按项目需要做跳过策略 |
| 真机走 `FSCTL_MOVE_FILE` | 裸块拷贝 | 裸拷贝不改 `$MFT` 的 runlist，文件系统必然损坏 |
| 搬前重新查一次布局 | 直接照扫描结果搬 | 扫描到执行之间文件可能被挪过，照旧计划搬会搬到错误位置 |
| 执行器用工厂注入 | 直接传执行器实例 | 执行器要拿 runner 的回调与限速器，那两样在 runner 构造完之后才有 |
| NTFS 路径忽略 op 内断点 | 按块续做 | MOVE_FILE 一次搬一段，中途失败是混合状态，跳块没有意义 |
| 保护判定收敛两次（规划+审计） | 只在规划时过滤 | "规划时过滤了"依赖每个调用方都记得，漏一处就是漏洞 |
| 系统卷默认放行、靠手输确认 | 默认禁止写系统卷 | 整理 C: 是主要用途；一刀切禁掉等于废掉产品 |
| 契约层用 frozen dataclass + Protocol | 直接共享引擎对象 | 引擎多线程读写，共享可变状态必然出竞态；frozen 让"事件是快照"成为编译期约束 |
| 规划按**文件**而不是按块 | 纯块级搬运 | 块级自由搬运会把文件拆得更碎，且没有文件边界就无法判断"搬完是否成功" |
| 目标区只用 first-fit | best-fit | 整理的目标本身就是往低地址聚拢；best-fit 会把文件撒开，反而更碎 |
| 断点原子替换而非追加 | 直接覆写 JSON | 掉电半截文件 = 断点作废，等于没做断点 |
| 取消/暂停绕过命令队列 | 全部走队列 | 队列由正在执行任务的线程消费，任务跑起来后没人读队列 |
| 单窗口单状态机 | 每功能一套 worker | 旧版 8 套 worker 各自判定生命周期，演化出"取消没反应/按钮永久禁用"一族缺陷 |
| 中央区可滚动 | 强制压缩布局 | 压缩会让卡片低于最小高度、子控件互相重叠；滚动是诚实的降级 |
| 对话框返回值**比数值**，不比身份 | `ret is QMessageBox.StandardButton.Yes` | PySide6 的 `question()` 返回的是 **int**（16384），身份比较恒为 False。见 8.1 |
| 冒烟必须走真实按钮闸门 | 无头环境绕过确认对话框，直接提交命令 | 绕过闸门 = 闸门永久无测试。2.0.0A 就是这么把"点开始整理没反应"放出去的 |

### 8.1 一次静默的"功能全坏"：枚举身份比较（2.0.0C 修复）

`QMessageBox.question()` 在 PySide6 6.12 上返回**普通 int**，不是
`StandardButton` 枚举成员。而四处判断写的是身份比较：

```python
if ret is QMessageBox.StandardButton.Yes:      # 恒 False
```

后果是四个功能同时"坏掉"，而且**全都不报错、不进日志**：

| 位置 | 用户看到的现象 |
| --- | --- |
| `_confirm_write` | 点「开始整理」→ 弹确认框 → 点「是」→ **什么都没发生** |
| `_elevate` | 点「提权」→ 弹确认框 → 点「是」→ **什么都没发生** |
| `_on_stop` | 点「停止」→ 点「是」→ 任务继续跑 |
| `closeEvent` | 运行中关窗口 → 点「是」→ 窗口关不掉 |

之所以一直没被发现：冒烟脚本当时刻意注释了"确认对话框在无头环境下无法交互，
因此这里绕过 `_on_start` 的确认闸门"。**绕过闸门的测试等于给闸门免检。**

现在的约束：

* 统一走 `main_window.confirmed(ret)`，比数值不比身份，非枚举输入一律当"否"；
* `scripts/smoke.py` 用桩替换 `QMessageBox`（返回 int Yes）并**调用真实的
  `_on_start()`**，把「点开始整理 → 任务真的跑起来」纳入冒烟；
* `tests/test_ui_contract.py::TestConfirmDialogs` 覆盖是/否两条分支、
  提权失败要把原因写进日志、开发态重启必须带脚本路径。


### 8.2 三个"界面一切正常但功能没生效"的缺陷（2.0.0L 修复）

共同点：**控件在、能点、不报错**，看起来只是"这个功能就是这样"。

**① 日志级别筛选是空壳**（`ui/widgets/log_view.py`）

两处叠加：

* `setCurrentIndex(1)` 写在 `connect` 之前，默认项从不触发过滤回调，内部阈值
  停在 `DEBUG` —— 下拉框显示「信息+」，实际一条都没滤；
* `_on_filter()` 的重画循环**不判断级别**，而 `append()` 又按当前阈值丢弃，
  于是「仅错误 → 全部」之后日志是空的（被丢的行再也回不来）。

修法的关键是分层：**存全量、渲染时过滤**。级别筛选是"看"的开关，不是"留"的
开关。同理，`plain_tail()`（复制诊断）从全量缓存取，不受筛选影响 —— 用户把
日志筛到「仅错误」正是因为他只想看错误，但求助时需要的是上下文。

**② 执行模式闸门跑在打开设备之后**（`engine/engine.py::_handle`）

`StartJob` 的顺序是「`_open` → `execute`」，而 `execute` 里的
`check_exec_mode()` 才拒绝"缓存搬运 + 已挂载 NTFS 卷"。于是设备构造函数先
抛「对原始卷写入必须先锁定卷（lock_volume=True）」—— 实现细节，读不出
"你选错了搬运方式"。现在闸门提到 `_open` 之前，并在界面上把这个组合直接
禁掉（`ParamsPanel.set_cache_allowed`）：可点却一定失败的选择比灰掉的控件更糟。

**③ 压实的统计口径在撒谎**（`engine/planner.py`）

真机报出三条互斥的结论：紧密段 0.0 MiB / 空隙 628 GiB（＞400 GiB 范围）/
还剩 400 GiB 未搬空。两个根因：

* 空隙按每次前置落点的落差**累加**，而游标不前移，各段互相包含 —— 换成
  `IntervalSet` 求并集；
* 「极端」档只挑大文件并把它们塞进前面的空洞，卷尾一个字节没动。压实只有
  数据真正贴上去才有价值，所以该档也要求紧贴：贴不上就什么都不搬，并说明
  换哪个档能解决。文案同时区分"有落位但没一个紧贴"与"压根没搬"。

### 8.3 两套缓存引擎的六个缺陷（2.0.0M 修复）

用户的原话是"我怀疑这个也可能有问题"。逐条查下来，问题不在算法，而在
**共享状态**与**"勾了但没接线"**这两类。

| # | 缺陷 | 后果 |
| --- | --- | --- |
| 1 | 内存缓存引擎被并发执行（`workers = concurrency`，默认 2） | `blocks_done` 是实例级计数，两个 op 交错时 A 的回写被算进 B → 断点记多了 → 续做**跳过没写的块** |
| 2 | `MemCacheConfig.from_params` 不传合并上限，默认 4 MiB | 单块设成 8/64 MiB（界面允许）时构造期抛 `ValueError`，`start_job` 直接失败 |
| 3 | 槽位在读写失败时不归还 | 失败攒够 `block_count` 次后 `_acquire_slot` 在空 `_dirty` 上 `popleft` → IndexError，IO 错误表现成"引擎崩了" |
| 4 | `_fill_cache` 被打断后照样跑第二阶段 | `preallocate` 把缓存文件扩到了最终大小，未写部分是**零** → 拿零覆盖目标区；断点续做时正好从零区长开始写 |
| 5 | 源短读直接写进缓存 | 与 `BlockDevice` 契约矛盾，后续数据整体错位（长度对、内容错） |
| 6 | 两条缓存路径都没有回读校验 | 界面上「校验=开」、诊断报告照抄，实际零次回读 |

修法与约束：

* **并发**：`MemCacheExecutor.serial_only = True`，调度器 `resolve_workers()`
  据此降到 1 并写一条日志；`run_op` 另外整段持 `RLock`（两道保险，因为
  "块池是实例级共享缓冲"这一点不会因为调用方改变而消失）。
* **配置**：合并上限取 `max(4 MiB, block_bytes)` —— 它必须是下限而不是定值。
* **池完整**：`_fill_slot` / `_flush_oldest` 的异常路径把槽位还回 `_free`；
  op 失败时 `_abandon_dirty()` 丢掉该 op 未回写的脏块（否则会被算进下一个 op）。
* **中断**：`_fill_cache` 返回**真正写进缓存的块数**，不足即拒绝进入第二阶段，
  并按"一个字节都没写"回报进度。
* **校验**：写完整批后回读比对；不一致抛 `VERIFY_MISMATCH`，错误分类不再
  写死 `RETRYABLE`（盲目重试只会再错一次）。
